# Отчёт по сквозному проекту

## Campus Search: семантический поиск по справочнику кампуса

**Дисциплина:** Инженерия искусственного интеллекта  
**Тема:** 5.2. Семантический поиск по набору документов `[INTERMEDIATE]`  
**Тип решения:** dense retrieval + векторный индекс + REST API (CLI / Swagger)  

---

## Аннотация

В работе реализован end-to-end сервис **Campus Search**, который по текстовому запросу пользователя находит наиболее релевантные фрагменты из локального корпуса нормативно-справочных текстов кампуса. Пайплайн включает подготовку данных, построение эмбеддингов на базе предобученного трансформера, индексацию в FAISS, офлайн-оценку качества (hit@K, MRR@K), сравнение альтернативных конфигураций и развёртывание FastAPI-сервиса с наблюдаемостью и контейнеризацией. Генерация готовых ответов языковой моделью не выполняется — возвращаются только найденные фрагменты с оценкой близости и идентификатором источника.

---

## 1. Постановка задачи

### 1.1. Предметная область

Студентам и сотрудникам вуза регулярно требуется информация из внутренних регламентов: порядок получения справок, правила проживания в общежитии, условия стипендий, режим работы библиотеки, подключение к Wi‑Fi, оформление академического отпуска. Тексты разрознены; формулировки вопросов пользователя не совпадают дословно с текстом документов.

### 1.2. Формулировка задачи

Построить систему **семантического поиска**:

- **Вход:** текстовый запрос на естественном языке (русский).
- **Выход:** упорядоченный список из top‑K фрагментов документов с полями `doc_id`, `title`, `chunk_text`, `score`.
- **Не в scope:** синтез ответа (RAG/LLM-чат), авторизация, администрирование корпуса.

### 1.3. Пользователи и сценарий

| Роль | Сценарий |
|------|----------|
| Пользователь / интегратор | REST API (`POST /search`, `POST /predict`) или CLI `client.py` |
| Разработчик | Пересборка индекса, offline-эксперименты, сравнение конфигураций |
| Оператор | `GET /health`, `GET /metrics`, логи сервиса |

### 1.4. Цели и метрики

**Бизнес-цель:** сократить время поиска нужного регламента за счёт семантического сопоставления запроса и фрагментов текста.

**Offline-метрики** (контрольный набор из **12** запросов с эталонными `relevant_doc_ids`):

- **hit@K** — доля запросов, для которых хотя бы один релевантный документ попал в top‑K;
- **MRR@K** (Mean Reciprocal Rank) — средняя обратная позиция первого релевантного документа в выдаче.

**Online-метрики** (эксплуатация сервиса):

- задержка обработки запроса (гистограмма Prometheus);
- счётчик запросов и кодов ответов;
- доступность компонентов (`GET /health`).

### 1.5. Ограничения и риски

| Ограничение | Влияние |
|-------------|---------|
| Небольшой корпус (18 документов) | Метрики на benchmark могут быть завышены; обобщение ограничено |
| Синтетические тексты | Нет гарантии переноса на реальный регламент без переиндексации |
| Семантическая близость ≠ юридическая релевантность | Нужен ручной benchmark и привязка к `doc_id` |
| Зависимость от внешней модели HF | Первый запуск требует сети; далее — локальный кэш |

## 2. Данные

### 2.1. Источник и формат

Корпус хранится в `data/knowledge_base.json` — массив объектов:

```json
{
  "doc_id": "campus_01",
  "title": "Справка об обучении",
  "text": "..."
}
```

Идентификаторы: `campus_01` … `campus_18`. Данные **синтетические**, подготовлены для учебного проекта; персональные сведения отсутствуют.

### 2.2. Тематическое покрытие

Документы охватывают типичные студенческие темы: справки и документы, общежитие, стипендии, библиотека, медпункт, IT-поддержка, Wi‑Fi, академический отпуск, военный учёт, перевод и отчисление, спорт, питание, внеучебная деятельность и др.

### 2.3. Разведочный анализ (EDA)

Анализ выполнен в `notebooks/experiments_retrieval.ipynb`.

| Показатель | Значение |
|------------|----------|
| Число документов | 18 |
| Пропуски в `doc_id`, `title`, `text` | нет |
| Длина `text` (символы), min / max | 287 / 356 |
| Средняя / медианная длина | 322.5 / 321.5 |
| Число чанков при `chunk_size=320`, `overlap=60` | 27 |

**Выводы EDA:** корпус однороден по объёму; длинные статьи отсутствуют — достаточно фиксированного чанкинга без сложной сегментации. Дубликатов и пустых полей не обнаружено.

### 2.4. Контрольный набор (benchmark)

Файл `artifacts/benchmark_queries.json` — **12** запросов с полями `query`, `relevant_doc_ids`, `query_type`:

- **keyword** (6) — формулировки с опорой на ключевые слова из текста;
- **paraphrase** (6) — перефразированные вопросы (например: *«где заказать документ, что я учусь в вузе»* → `campus_01`).

Набор используется для сравнения **dense**, **BM25** и **hybrid** на одном протоколе.

## 3. Методы и реализация

### 3.1. Пайплайн подготовки

1. **Загрузка** корпуса (`aie_rag.data.kb.load_kb`).
2. **Чанкинг** — скользящее окно по символам: параметры `chunk_size`, `overlap`.
3. **Эмбеддинг** — модель `paraphrase-multilingual-MiniLM-L12-v2` (Sentence Transformers), L2-нормировка векторов.
4. **Индексация** — FAISS `IndexFlatIP` (скалярное произведение нормированных векторов эквивалентно косинусной близости).
5. **Сериализация** — `faiss.index`, `chunks.json`, `meta.json`.

Скрипт сборки: `python -m aie_rag.scripts.build_index`.

### 3.2. Онлайн-поиск (dense)

1. Эмбеддинг запроса той же моделью.
2. Поиск top‑K в FAISS.
3. Обогащение результатов метаданными чанка (`doc_id`, `title`, `chunk_text`).

### 3.3. Альтернативные retriever (для экспериментов)

| Retriever | Описание |
|-----------|----------|
| **dense** | Эмбеддинги + FAISS (основной) |
| **bm25** | Лексический поиск Okapi BM25 по токенам чанков |
| **hybrid** | Reciprocal rank fusion (RRF) по объединению dense и BM25 |

Переключение при оценке: переменная окружения `AIE_RAG_RETRIEVER`.

### 3.4. Обоснование выбора компонентов

- **MiniLM multilingual** — компактная модель с поддержкой русского, приемлемая задержка на CPU.
- **IndexFlatIP** — для 27 чанков точный перебор быстрее и проще, чем IVF/HNSW.
- **Чанкинг с overlap** — снижает риск «разрезания» ответа между границами чанков.

## 4. Эксперименты

### 4.1. Протокол

| Параметр | Значение |
|----------|----------|
| Метрики | hit@5, MRR@5 |
| Benchmark | 12 запросов (6 keyword + 6 paraphrase) |
| Сетка конфигураций | `chunk_size` ∈ {200, 320} × `chunk_overlap` ∈ {40, 60} × retriever ∈ {dense, bm25, hybrid} → **12 прогонов** |
| Скрипт | `python -m aie_rag.scripts.run_experiments` |
| Ноутбук | `notebooks/experiments_retrieval.ipynb` (EDA + визуализация) |

**Артефакты:**

- `artifacts/retrieval_experiment_matrix.csv` — полная матрица;
- `artifacts/retrieval_per_query_<retriever>_320_60.csv` — разбивка по запросам;
- `artifacts/figures/*.png` — графики MRR;
- `artifacts/retrieval_experiments_summary.csv` — сводка retriever при 320/60.

Воспроизведение: рекомендуемый путь — `pip install -e .` из каталога `project/` (тогда `PYTHONPATH` не нужен). Альтернатива без установки — `PYTHONPATH=src`.

### 4.2. Матрица экспериментов (фрагмент, production overlap=60)

| chunk_size | retriever | hit@5 | mrr@5 |
|------------|-----------|-------|-------|
| 200 | dense | 1.00 | 0.90 |
| 200 | bm25 | 0.83 | 0.83 |
| 200 | hybrid | 0.92 | 0.88 |
| 320 | dense | 1.00 | **0.96** |
| 320 | bm25 | 0.83 | 0.79 |
| 320 | hybrid | 1.00 | 0.90 |

Полная таблица (включая overlap=40) — в `retrieval_experiment_matrix.csv`.

**Вывод по chunk_size (dense, overlap=60):** hit@5=1.0 для 200 и 320; **mrr@5** выше у **320** (0.96 vs 0.90) — релевантный документ стабильнее в верхних позициях.

**Вывод по retriever (320/60):** **dense** лидирует по hit@5 и mrr@5; **BM25** пропускает часть запросов (hit@5=0.83), особенно на перефразированных формулировках; **hybrid** улучшает BM25, но не превосходит dense по MRR на этом корпусе.

### 4.3. Анализ по типу запроса (dense, 320/60)

Агрегация по `query_type` из `retrieval_per_query_dense_320_60.csv`:

| query_type | Средний hit@5 | Средний mrr@5 |
|------------|---------------|---------------|
| keyword | 1.00 | 1.00 |
| paraphrase | 1.00 | 0.92 |

На перефразированном запросе *«прервать обучение из-за здоровья как оформить»* релевантный `campus_13` найден, но на **2-й позиции** (mrr=0.5) — типичный случай для тонкой настройки ранжирования.

Для **BM25** (320/60) средний hit@5 на paraphrase-запросах ниже, чем у dense — подтверждает выбор семантического retriever для продакшн-сервиса.

### 4.4. Связь с этапами overview (адаптация для retrieval)

| Этап overview | Реализация в проекте |
|---------------|---------------------|
| Базовые модели | BM25 (лексический baseline) |
| Нейросетевой компонент | Предобученный трансформер (эмбеддинги) + FAISS |
| Настройка гиперпараметров | `chunk_size`, `chunk_overlap`, выбор retriever |
| Учёт экспериментов | CSV-матрица + графики (аналог MLflow для учебного масштаба) |

### 4.5. Интерпретация

Эксперименты показывают **измеримую разницу** между BM25 и dense на расширенном benchmark (не все метрики равны 1.0 для всех конфигураций). Корпус по-прежнему учебный (18 документов); для промышленного использования нужны больший корпус и расширенный набор контрольных запросов.

## 5. Выбор финальной конфигурации

**Принятая конфигурация для сервиса:**

| Параметр | Значение |
|----------|----------|
| Retriever | dense |
| Модель эмбеддингов | `paraphrase-multilingual-MiniLM-L12-v2` |
| chunk_size | 320 |
| chunk_overlap | 60 |
| top_k (по умолчанию в API) | 5 |
| Индекс | FAISS IndexFlatIP |

**Критерии выбора:**

1. Максимальный **mrr@5** среди вариантов chunk_size при hit@5=1.0.
2. Простота эксплуатации (один векторный индекс, без отдельного лексического индекса в runtime).
3. Соответствие постановке «семантический поиск» и устойчивость к перефразированию.
4. Приемлемое время отклика на CPU в учебной среде.

## 7. API-сервис

### 7.1. Стек

FastAPI, Uvicorn, Pydantic v2, prometheus-client.

### 7.2. Endpoints

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/` | Краткая справка по API (JSON) |
| POST | `/search` | Основной поиск |
| POST | `/predict` | Поиск (тот же контракт) |
| GET | `/health` | Статус артефактов |
| GET | `/metrics` | Метрики Prometheus |

### 7.3. Поведение при ошибках

- Отсутствие индекса → HTTP **503** с указанием команды `build_index`.
- Пустой или слишком длинный запрос → валидация Pydantic (**422**).

При старте индекс загружается в память один раз (`lru_cache`), что снижает задержку повторных запросов.

## 8. Наблюдаемость

- **Логирование:** модуль `aie_rag.core.logging`, уровень из `AIE_RAG_LOG_LEVEL`; логи HTTP-клиента и загрузки модели.
- **Health-check:** проверка наличия обязательных файлов в `artifacts_dir`.
- **Метрики Prometheus:**
  - `aie_rag_requests_total{endpoint, status}` — счётчик запросов;
  - `aie_rag_request_latency_seconds{endpoint}` — гистограмма задержек.

Это покрывает минимальные требования к эксплуатационной готовности учебного сервиса.

## 12. Ограничения и план развития

**Текущие ограничения:**

- малый корпус и benchmark;
- нет автоматического обновления индекса при изменении JSON;
- нет reranker второго уровня;
- нет мультиязычного UI и обратной связи пользователя.

**Возможные шаги развития:**

- расширение корпуса и benchmark (50+ запросов);
- cross-encoder reranking;
- периодическая переиндексация и версионирование артефактов;
- опциональный RAG-слой (генерация ответа поверх найденных фрагментов);
- деплой в оркестратор (Kubernetes) с мониторингом SLA.

Финальная конфигурация: **dense**, chunk 320/60, MiniLM + FAISS — по результатам матрицы экспериментов и критериям сопровождения.
